# RAG 基础概念

## 一句话结论

RAG 是让模型先检索外部资料，再基于检索结果生成答案的方法；它的价值不是让模型“更聪明”，而是让回答更依赖可更新、可追溯、可验证的外部知识。

## 概念定位

- 它是什么：一种把信息检索和文本生成结合起来的系统方法。
- 它不是什么：不是把整本文档直接塞进 prompt，也不是保证模型永远不幻觉的万能药。
- 相邻概念：semantic search、embedding、vector database、file search、question answering、long context、fine-tuning、tool calling。
- 前置知识：大语言模型、prompt、token、embedding、检索、上下文窗口、引用来源。

初学者可以先记住：

```text
不用 RAG：模型主要靠训练时学到的知识回答。
使用 RAG：模型先去你的资料里找依据，再根据依据回答。
```

## 缩写全称速查

| 缩写 | 英文全称 | 中文解释 | 初学者理解 |
| --- | --- | --- | --- |
| RAG | Retrieval-Augmented Generation | 检索增强生成 | 先检索相关资料，再让模型基于资料生成回答 |
| LLM | Large Language Model | 大语言模型 | 负责理解问题和生成答案的模型 |
| NLP | Natural Language Processing | 自然语言处理 | 让计算机处理人类语言的技术领域 |
| QA | Question Answering | 问答 | 根据问题给出答案的任务 |
| IR | Information Retrieval | 信息检索 | 从大量资料里找出相关内容 |
| API | Application Programming Interface | 应用程序编程接口 | 调用模型、检索工具或向量库的程序接口 |
| UI | User Interface | 用户界面 | 展示答案、引用、加载状态和错误的界面 |
| KB | Knowledge Base | 知识库 | 存放资料、笔记、文档和结构化知识的地方 |

注意：RAG 里的 `Retrieval` 是“检索”，不是“模型回忆”；`Generation` 是“生成”，不是“复制原文”。两者结合，才是 RAG。

## 核心概念

RAG 解决的是大模型应用中的一个核心矛盾：

```text
模型会生成语言，但它不天然知道你的最新资料、内部文档和个人知识。
```

如果只靠模型训练时学到的知识，会遇到几个问题：

- 资料可能过时。
- 模型不知道你的私有文件。
- 模型可能编造不存在的依据。
- 很难追溯答案来自哪里。
- 更新知识不方便，每次都靠微调成本很高。

RAG 的思路是把“知识”放在模型外部：

```text
外部知识库负责存资料。
检索系统负责找相关片段。
大模型负责理解问题、整合资料、组织答案。
```

这就是 RAG 原论文里“参数化记忆”和“非参数化记忆”的直觉：

- 参数化记忆：模型权重里学到的知识。
- 非参数化记忆：外部文档库、搜索索引、数据库等可更新资料。

## 机制与原理

一个最小 RAG 系统通常分成两个阶段。

### 阶段 1：离线准备资料

```text
原始文档
  -> 清洗
  -> 切分成 chunk
  -> 生成 embedding
  -> 写入索引或向量库
```

这一步不是用户每问一次都重新做，而是在资料进入知识库时做。

### 阶段 2：在线回答问题

```text
用户问题
  -> 问题理解或改写
  -> 检索相关 chunk
  -> 排序或重排
  -> 拼成上下文
  -> 模型基于上下文回答
  -> 展示引用和不确定性
```

RAG 的质量取决于两件事：

1. 检索是否找到了真正相关、足够完整、可信的资料。
2. 模型是否真的被这些资料约束，而不是继续凭空发挥。

如果检索阶段拿错资料，后面的模型再强也可能答错。这叫 garbage in, garbage out，意思是“输入垃圾，输出也很可能是垃圾”。

## 适用场景

- 知识经常变化：政策、产品文档、价格、接口说明、内部流程。
- 知识属于个人或组织私有：个人笔记、公司文档、项目代码、客服知识库。
- 答案需要引用来源：学习笔记、合规问答、技术支持、研究助手。
- 不适合或没必要微调：只是补知识，不是改模型行为风格。
- 资料量超过上下文窗口：不能每次把所有文档都放进 prompt。

## 不适用场景

- 问题不需要外部知识，例如简单改写、翻译、格式整理。
- 资料质量很差、没有来源、互相冲突，却要求模型给确定答案。
- 任务主要是执行动作，例如发邮件、查订单、部署代码，tool calling 更关键。
- 需要强格式稳定性或风格定制，可能应先考虑 prompt、structured output 或 fine-tuning。
- 资料高度结构化，普通数据库查询比语义检索更准确。

## 前提、边界与反例

- 必要前提：有可检索的资料、资料质量可接受、切分合理、检索结果能回传给模型。
- 适用边界：RAG 能改善外部知识访问，但不能自动判断资料真伪。
- 反例或例外：如果答案必须来自精确数据库字段，例如账户余额，应直接查数据库，不应只靠 RAG 文本检索。
- 结论可能失效的条件：资料过时、切分丢上下文、检索召回失败、模型忽略引用、用户问题过于模糊。

## 对比与替代方案

| 方案 | 解决什么 | 优点 | 局限 |
| --- | --- | --- | --- |
| Prompt-only | 写清任务要求 | 简单、快 | 不能补充模型不知道的资料 |
| Long context | 把大量资料放进上下文 | 实现直观 | 成本高，仍需要选择资料和防止注意力稀释 |
| RAG | 从资料库检索相关上下文 | 可更新、可引用、可扩展 | 检索和上下文构造会失败 |
| Fine-tuning | 调整模型行为或格式 | 输出风格更稳定 | 不适合频繁更新事实知识 |
| Database query | 精确查询结构化数据 | 准确、可审计 | 不擅长开放语义问题 |
| Tool calling | 执行外部动作或查询 | 可控、能行动 | 不等于知识检索本身 |

## 示例或最小实验

假设你有一个 Markdown 知识库，里面有一篇 RLHF 笔记。

用户问：

```text
RLHF 是什么？它和 SFT 有什么区别？
```

RAG 流程应该是：

```text
1. 搜索知识库中和 RLHF、SFT 相关的笔记。
2. 找到 `05-RLHF人类反馈强化学习.md` 和 `04-SFT监督微调.md`。
3. 读取相关段落，而不是整章全部塞给模型。
4. 让模型只基于这些段落回答。
5. 回答里标注来源文件。
6. 如果资料没有覆盖某个点，就明确说“当前知识库没有说明”。
```

一个好回答应该像：

```text
根据你的 RLHF 笔记，RLHF 是 Reinforcement Learning from Human Feedback，即基于人类反馈的强化学习。它和 SFT 的区别是：SFT 主要让模型模仿人工示范答案，RLHF 则让模型根据人类偏好或奖励模型优化回答倾向。

来源：knowledge/01-大模型的使用与训练/05-RLHF人类反馈强化学习.md
```

一个坏回答是：

```text
RLHF 是一种让模型自动搜索互联网并自我训练的方法。
```

问题在于它既没有来源，也把 RLHF 说错了。

## 失败模式与风险

- 检索不到：资料里明明有答案，但搜索没召回。
- 检索错：拿到了看似相关但实际不支持答案的片段。
- 上下文不足：检索到了片段，但缺少前后文，模型误解。
- 资料过时：旧资料被当作最新事实。
- 引用幻觉：模型给出不存在或不支持答案的来源。
- 答案脱离资料：检索结果正确，模型却凭常识扩写。
- 冲突未处理：不同资料说法冲突，模型强行合并。
- 权限泄露：检索到了用户不该看的文档。

## 常见误区

- 误区：RAG 可以彻底解决幻觉。
  - 修正：RAG 能降低一部分知识幻觉，但检索错、资料错、模型忽略资料时仍会幻觉。
- 误区：资料越多越好。
  - 修正：资料越多，噪声和过时内容也越多。质量、结构和 metadata 很重要。
- 误区：把整篇文档塞给模型就是 RAG。
  - 修正：RAG 强调检索相关内容，不是无差别塞上下文。
- 误区：用了向量数据库就是 RAG。
  - 修正：向量数据库只是检索基础设施，RAG 还包括切分、排序、上下文、生成、引用和评估。
- 误区：RAG 比微调永远更好。
  - 修正：RAG 适合补外部知识，微调更适合稳定行为、格式和风格。

## 实践判断

- 什么时候应该采用：答案依赖外部资料、资料会更新、需要引用、内容多到不能全放进 prompt。
- 什么时候应该谨慎：资料来源不可靠、权限复杂、答案必须严格准确但资料本身不完整。
- 落地时最先验证什么：能否召回正确资料；模型是否只基于资料回答；引用是否真实。
- 可观察指标或检查点：召回率、引用准确率、无答案拒答率、上下文命中率、人工满意度、幻觉率。

## 待验证问题

- 对本知识库来说，RAG 是否应该先基于 Markdown 标题检索，再做向量检索。
- 中文学习笔记的最佳 chunk 粒度是小节、段落还是固定 token。
- 如果资料互相冲突，知识库问答应该如何展示冲突而不是强行总结。
- GitHub Pages 静态站是否适合做纯前端本地搜索，还是应另建后端检索服务。
