# 文档切分与索引

## 一句话结论

文档切分与索引决定 RAG 能不能找到“刚好够用”的资料；切得太粗会引入噪声，切得太碎会丢上下文，metadata 和索引维护不到位则会让答案不可追溯或过时。

## 概念定位

- 它是什么：把原始资料清洗、拆分、标注、向量化并写入可检索索引的过程。
- 它不是什么：不是简单按固定字数切文本，也不是把所有文件一次性丢进向量库就结束。
- 相邻概念：chunk、metadata、embedding、vector index、inverted index、reranking、hybrid search。
- 前置知识：RAG、token、embedding、文档结构、文件格式、来源管理。

初学者可以先记住：

```text
RAG 回答质量的一半，在模型调用前就已经被文档处理决定了。
```

## 缩写全称速查

| 缩写 | 英文全称 | 中文解释 | 初学者理解 |
| --- | --- | --- | --- |
| RAG | Retrieval-Augmented Generation | 检索增强生成 | 先检索资料再生成答案 |
| OCR | Optical Character Recognition | 光学字符识别 | 把图片或扫描 PDF 里的文字识别出来 |
| PDF | Portable Document Format | 便携式文档格式 | 常见文档格式，但结构解析经常复杂 |
| HTML | HyperText Markup Language | 超文本标记语言 | 网页文档格式，包含标题、链接、段落等结构 |
| Markdown | Markdown | 轻量标记语言 | 本知识库使用的文本格式，标题结构很适合切分 |
| CSV | Comma-Separated Values | 逗号分隔值 | 表格数据格式 |
| JSON | JavaScript Object Notation | JavaScript 对象表示法 | 结构化数据格式，常用于 metadata |
| ID | Identifier | 标识符 | 唯一标记文档、chunk 或索引记录 |
| BM25 | Best Matching 25 | 经典稀疏检索排序函数 | 关键词检索常用算法 |
| MMR | Maximal Marginal Relevance | 最大边际相关性 | 在相关性和多样性之间选结果，减少重复 chunk |
| ETL | Extract, Transform, Load | 抽取、转换、加载 | 数据进入系统前的清洗和写入流程 |

Chunk 不是缩写。它指“文档片段”。在 RAG 里，一个 chunk 通常是模型检索和引用的最小文本单元。

## 核心概念

### 1. Chunk

Chunk 是切分后的文档片段。一个 chunk 应该尽量满足：

- 包含一个相对完整的意思。
- 不太长，能放进上下文。
- 不太短，保留必要前后文。
- 能追溯回原始文档位置。

坏 chunk：

```text
它很重要。因此应该这样做。
```

问题：不知道“它”指什么。

好 chunk：

```text
RAG 的检索阶段应该返回能支持答案的资料片段。如果片段缺少上下文，模型可能误解代词、标题或前提条件。
```

### 2. Metadata

Metadata 是“关于数据的数据”。它不一定进入模型回答，但对检索、过滤、引用、权限非常关键。

常见 metadata：

| 字段 | 作用 |
| --- | --- |
| `source_path` | 来源文件路径 |
| `title` | 文档标题 |
| `section` | 所在章节 |
| `chunk_id` | chunk 唯一标识 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `source_url` | 外部来源 |
| `access_level` | 权限等级 |
| `tags` | 主题标签 |

没有 metadata 的 RAG，很容易变成“模型说资料里有，但你找不到资料在哪”。

### 3. Index

Index 是索引，让系统能快速找资料。

常见索引类型：

- 关键词索引：适合精确词、标题、术语、编号。
- 向量索引：适合语义相似。
- 混合索引：关键词和向量一起用。
- 结构化索引：数据库字段、时间、权限、标签。

真实系统经常不是“一个向量库解决所有问题”，而是多个索引配合。

## 机制与原理

文档进入 RAG 系统的一般流程：

```text
1. Ingest：读取原始文档
2. Parse：解析文本、标题、表格、代码块
3. Clean：去掉噪声、页眉页脚、重复内容
4. Split：按结构或语义切成 chunk
5. Enrich：补 metadata、标签、来源、权限
6. Embed：为 chunk 生成 embedding
7. Index：写入关键词索引和向量索引
8. Validate：抽样检查 chunk 是否可读、可追溯、可检索
```

### 切分策略

| 策略 | 说明 | 适合 | 风险 |
| --- | --- | --- | --- |
| 固定长度切分 | 按字符或 token 数切 | 快速原型 | 容易切断语义 |
| 标题结构切分 | 按 Markdown/HTML 标题切 | 文档、知识库 | 小节太长时还要二次切分 |
| 段落切分 | 按自然段切 | 文章、笔记 | 段落长短不一 |
| 语义切分 | 按主题变化切 | 长文档、教程 | 实现更复杂 |
| 代码结构切分 | 按函数、类、文件切 | 代码库 | 需要语言解析器 |
| 表格行块切分 | 按表头和行组切 | 表格资料 | 易丢列含义 |

### Chunk size 和 overlap

Chunk size 是每个片段大小。Overlap 是相邻 chunk 之间重复保留的部分。

```text
chunk 1: A B C D
chunk 2: D E F G
```

这里 `D` 就是 overlap。它能减少切断上下文的问题，但 overlap 太大也会导致重复和成本增加。

经验判断：

- 概念型笔记：按标题和小节切分通常更自然。
- FAQ：一问一答可以作为 chunk。
- 技术文档：标题、代码块、参数表要尽量保留在一起。
- 法律/合同：条款编号和上下文必须保留。
- 表格：表头要和行数据一起进入 chunk，否则模型不知道列含义。

## 适用场景

- 建个人知识库、企业文档问答、客服知识库、代码问答、研究资料库。
- 文档数量多，无法每次手动选择资料。
- 需要引用具体来源和位置。
- 文档会更新，需要可维护的索引刷新策略。
- 需要按权限、时间、标签或项目过滤检索结果。

## 不适用场景

- 只有几篇短文档，手动选择上下文可能更简单。
- 资料高度结构化，直接数据库查询更可靠。
- 原始文档质量极差，OCR 错误、乱码、重复内容未处理。
- 文档权限不清楚，不能安全进入统一索引。
- 业务还没确定，过早设计复杂索引会浪费时间。

## 前提、边界与反例

- 必要前提：文档能解析成文本，来源和权限可记录，chunk 能追溯回原文。
- 适用边界：好的切分能提高检索质量，但不能修复错误资料本身。
- 反例或例外：一张包含关键数字的表格，如果按普通文本切碎，可能比不做 RAG 更危险。
- 结论可能失效的条件：文档格式复杂、标题结构混乱、更新流程不稳定、旧索引未删除。

## 对比与替代方案

| 方案 | 优势 | 劣势 | 适合场景 |
| --- | --- | --- | --- |
| 手动选择上下文 | 最可控 | 不可扩展 | 少量资料、重要单次任务 |
| 固定长度 chunk | 实现快 | 语义断裂 | 快速原型 |
| 结构化切分 | 可读、可追溯 | 依赖文档结构 | Markdown、HTML、技术文档 |
| 语义切分 | 更贴近主题 | 成本和复杂度高 | 长篇文章、课程 |
| 数据库字段索引 | 精确可靠 | 不擅长开放语义 | 订单、用户、库存 |
| 混合索引 | 召回更稳 | 系统复杂 | 生产知识库 |

## 示例或最小实验

对本知识库的 Markdown 文件，可以先用标题结构切分。

例如：

```markdown
# RAG 基础概念

## 一句话结论
...

## 核心概念
...

## 失败模式与风险
...
```

可以生成 chunk：

```json
{
  "chunk_id": "03-rag-01-core-concepts",
  "source_path": "knowledge/03-RAG与知识库检索/01-RAG基础概念.md",
  "title": "RAG 基础概念",
  "section": "核心概念",
  "text": "RAG 解决的是大模型应用中的一个核心矛盾..."
}
```

这样用户问“RAG 为什么不能解决所有幻觉”时，系统可以检索到 `失败模式与风险` 或 `常见误区` 小节，而不是整篇文档。

## 失败模式与风险

- 切分太粗：一个 chunk 包含多个主题，检索到后噪声很大。
- 切分太碎：模型看不到定义、前提和反例。
- 标题丢失：chunk 内容缺少所属章节，模型不知道语境。
- 表格拆坏：行和表头分离，数字没有含义。
- 代码块拆坏：函数签名和解释分离。
- Metadata 缺失：无法引用来源、无法按权限过滤。
- 索引陈旧：文档更新后旧 chunk 仍被检索。
- 重复 chunk：多个相似片段挤占 top-k，导致多样性不足。
- 权限混入：私有资料进入公共索引。
- 编码问题：中文、符号、代码、表格在解析时损坏。

## 常见误区

- 误区：chunk size 有一个通用最佳值。
  - 修正：最佳粒度依赖文档结构、问题类型、模型上下文和引用需求。
- 误区：overlap 越大越好。
  - 修正：overlap 太大会增加重复、成本和噪声。
- 误区：只要向量化了就能搜好。
  - 修正：解析、切分、metadata 和索引刷新同样重要。
- 误区：PDF 解析出来的文本一定可靠。
  - 修正：PDF 可能有页眉页脚、断行、表格错位和 OCR 错误。
- 误区：metadata 只是辅助信息。
  - 修正：metadata 决定引用、权限、过滤、排序和维护能力。

## 实践判断

- 什么时候应该采用结构化切分：Markdown、HTML、技术文档、课程材料。
- 什么时候应该谨慎：扫描 PDF、复杂表格、法律条款、代码仓库、多语言混排。
- 落地时最先验证什么：随机抽 20 个 chunk，看是否可读、完整、能追溯、能被正确问题检索到。
- 可观察指标或检查点：chunk 平均长度、空 chunk 比例、重复率、召回率、引用可追溯率、索引刷新延迟。

## 待验证问题

- 本知识库 Markdown 最适合按二级标题还是三级标题切分。
- 代码块和表格是否需要作为独立 chunk。
- 是否应该保留 `变更记录` 进入检索，还是只作为审计 metadata。
- viewer 是否可以显示 chunk 来源位置，而不只是文件路径。
