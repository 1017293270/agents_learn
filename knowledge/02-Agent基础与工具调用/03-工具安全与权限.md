# 工具安全与权限

## 一句话结论

Agent 工具安全的核心是：模型只能提出工具调用意图，真实执行必须由应用侧根据用户身份、工具风险、参数语义、业务规则和审计要求来决定是否允许。

## 概念定位

- 它是什么：围绕 agent 工具调用建立的一套权限、确认、验证、审计和回滚机制。
- 它不是什么：不是在 prompt 里写一句“不要做危险操作”就结束，也不是完全相信模型会自己判断风险。
- 相邻概念：tool calling、guardrails、access control、least privilege、audit log、prompt injection、data leakage。
- 前置知识：API、JSON Schema、用户身份、服务端鉴权、业务权限、错误处理、日志。

初学者可以先记住：

```text
模型负责“想做什么”。
应用负责“能不能做、怎么安全地做、做完如何追踪”。
```

## 缩写全称速查

| 缩写 | 英文全称 | 中文解释 | 初学者理解 |
| --- | --- | --- | --- |
| API | Application Programming Interface | 应用程序编程接口 | 工具通常就是应用暴露给 agent 的 API 或函数 |
| JSON | JavaScript Object Notation | JavaScript 对象表示法 | 工具参数常用 JSON 表达 |
| RBAC | Role-Based Access Control | 基于角色的访问控制 | 根据用户角色决定权限，例如 admin 可以审批，普通用户只能查看 |
| ABAC | Attribute-Based Access Control | 基于属性的访问控制 | 根据用户、资源、时间、部门、风险等级等属性判断权限 |
| ACL | Access Control List | 访问控制列表 | 资源上记录哪些用户或组能访问 |
| PII | Personally Identifiable Information | 个人可识别信息 | 能识别个人身份的数据，如手机号、身份证号、邮箱 |
| DLP | Data Loss Prevention | 数据泄露防护 | 防止敏感数据被错误输出、上传或发送 |
| SSRF | Server-Side Request Forgery | 服务端请求伪造 | 攻击者诱导服务器访问不该访问的内部地址 |
| SQL | Structured Query Language | 结构化查询语言 | 数据库查询语言，工具拼接 SQL 时必须防注入 |
| XSS | Cross-Site Scripting | 跨站脚本攻击 | 恶意内容被页面执行，常见于 HTML/Markdown 渲染 |
| CSRF | Cross-Site Request Forgery | 跨站请求伪造 | 诱导用户浏览器在不知情时发起操作 |
| TTL | Time To Live | 生存时间 | 临时权限、缓存或 token 的有效时间 |
| MFA | Multi-Factor Authentication | 多因素认证 | 高风险操作前额外验证身份，例如短信、验证器、硬件密钥 |

注意：OAuth 常被解释为 Open Authorization，但更严谨地说，OAuth 是一个授权协议名称，不要把它误解成“登录协议”。登录通常还会涉及 OpenID Connect。

## 核心概念

### 1. 权限边界

工具权限不应该由模型决定，而应该由服务端策略决定。常见边界包括：

- 用户身份：当前用户是谁。
- 用户角色：管理员、成员、访客、审计员。
- 资源归属：订单、文件、项目是否属于当前用户或组织。
- 动作类型：读取、创建、更新、删除、发布、付款、发消息。
- 风险等级：是否不可逆、是否影响他人、是否外发数据。
- 运行环境：开发、测试、生产。

### 2. 最小权限原则

Least privilege，全称是最小权限原则。意思是：工具只获得完成当前任务所需的最小权限。

错误做法：

```text
给 agent 一个万能数据库工具：run_any_sql(query)
```

更安全做法：

```text
给 agent 一个受限工具：get_current_user_order_status(order_id)
```

前者让模型能构造任意查询，风险极高；后者只允许查询当前用户订单状态，参数和权限都更容易验证。

### 3. 工具风险分级

| 风险等级 | 工具类型 | 处理方式 |
| --- | --- | --- |
| 低风险 | 查询公开资料、计算、格式转换 | 参数校验和日志即可 |
| 中风险 | 查询用户私有数据、生成草稿、读取项目文件 | 身份校验、资源权限、敏感信息过滤 |
| 高风险 | 删除、付款、发消息、改权限、部署生产 | 二次确认、强审计、可回滚或人工审批 |
| 禁止 | 绕过权限、窃取密钥、访问无授权资源 | 直接拒绝，不交给模型自由处理 |

### 4. Guardrails 护栏

Guardrails 指输入、输出和行动边界上的防护规则。它可以包括：

- 输入护栏：检查用户请求是否要求越权、违法或危险操作。
- 工具前护栏：工具执行前验证参数、权限和风险等级。
- 工具后护栏：过滤工具返回中的敏感数据。
- 输出护栏：防止模型把敏感信息、内部错误或危险指令输出给用户。
- 人工升级：当风险高或不确定时，交给人确认。

## 机制与原理

一个安全 tool calling 流程应该像这样：

```text
1. 模型生成 tool call
2. 应用解析工具名和参数
3. schema 校验：字段是否存在，类型是否正确
4. 语义校验：订单号、路径、金额、收件人是否合理
5. 权限校验：当前用户是否允许访问该资源
6. 风险分级：是否高风险、是否需要确认
7. 执行工具：带超时、重试、幂等和错误处理
8. 输出过滤：删除不该回传给模型或用户的敏感字段
9. 审计记录：记录谁、何时、为什么、调用什么、结果如何
10. 回传模型或展示给用户
```

其中第 3 步和第 4 步经常被混淆。Schema 校验只能保证“形状正确”，不能保证“业务正确”。

比如：

```json
{
  "order_id": "A-10086"
}
```

这个参数形状可能正确，但仍然需要检查：

- 这个订单是否存在。
- 这个订单是否属于当前用户。
- 当前用户是否有查看权限。
- 查询结果是否包含不该暴露的 PII。

## 适用场景

- Agent 可以读取或修改用户、组织、项目、订单、文件、代码或生产资源。
- 工具会调用外部 API、数据库、浏览器、文件系统或消息系统。
- 工具结果会进入模型上下文，可能被模型引用或输出给用户。
- 系统需要满足合规、审计、权限隔离或企业安全要求。
- 用户需要看到 agent 正在做什么，并能取消、确认或回滚。

## 不适用场景

严格说，工具安全与权限没有“不适用”。只要 agent 有工具，就需要某种安全边界。区别只在于强度：

- 纯本地、无副作用、无敏感数据的玩具实验，可以只做轻量日志和参数校验。
- 面向真实用户、真实数据、真实动作的系统，必须做完整权限、确认和审计。

## 前提、边界与反例

- 必要前提：用户身份可信、资源归属清楚、工具风险可分类、服务端能拒绝越权操作。
- 适用边界：权限控制能降低风险，但不能保证模型永远不提出危险意图。
- 反例或例外：如果工具只做数学计算，权限模型可以很轻；但仍应限制输入大小和运行时间。
- 结论可能失效的条件：工具本身有漏洞、权限规则错误、日志泄露敏感数据、确认界面误导用户。

## 对比与替代方案

| 方案 | 说明 | 优点 | 风险 |
| --- | --- | --- | --- |
| Prompt 约束 | 告诉模型不要做危险事 | 简单 | 不可靠，不能作为唯一安全机制 |
| Schema 校验 | 限制参数形状 | 必须做，能减少格式错误 | 不能保证业务语义正确 |
| 服务端权限 | 后端按用户和资源判断 | 可靠、可审计 | 需要完整权限模型 |
| 人工确认 | 高风险动作前让用户确认 | 可控，适合不可逆动作 | 增加摩擦，确认文案要清楚 |
| 沙箱执行 | 在隔离环境运行工具 | 降低系统破坏风险 | 不能替代权限和数据治理 |
| 禁用工具 | 不给 agent 高风险能力 | 最安全 | 降低自动化能力 |

## 示例或最小实验

### 不安全工具

```typescript
{
  name: "delete_file",
  description: "Delete any file by path.",
  parameters: {
    type: "object",
    properties: {
      path: { type: "string" }
    },
    required: ["path"]
  }
}
```

风险：

- 任意路径删除。
- 没有用户确认。
- 没有工作区边界。
- 没有审计。
- 模型可能被间接提示注入诱导删除重要文件。

### 更安全工具

```typescript
{
  name: "delete_workspace_draft",
  description: "Delete a draft file owned by the current user inside the workspace.",
  parameters: {
    type: "object",
    properties: {
      draft_id: { type: "string" },
      reason: { type: "string" }
    },
    required: ["draft_id", "reason"],
    additionalProperties: false
  },
  risk: "high",
  requires_confirmation: true
}
```

应用侧还要做：

```text
1. 根据 draft_id 查真实文件路径。
2. 确认文件属于当前用户。
3. 确认文件位于允许目录。
4. 给用户展示将删除的文件名和原因。
5. 用户确认后执行删除。
6. 写入 audit log。
7. 提供恢复或备份路径。
```

## 失败模式与风险

- 越权读取：agent 查询了当前用户不该看的数据。
- 越权写入：agent 修改了他人资源。
- 参数幻觉：模型编造资源 ID，服务端没有拦截。
- 间接提示注入：网页或文档让模型忽略规则、调用危险工具。
- 数据泄露：工具返回 PII，模型原样输出。
- SSRF：工具允许任意 URL 请求，访问了内部服务。
- SQL 注入：工具把模型生成的查询拼接进数据库。
- 高风险误操作：模型发错消息、删错文件、改错权限。
- 日志泄露：audit log 记录了密钥、token、隐私数据。
- 确认疲劳：用户频繁确认，最后不认真看高风险提示。

## 常见误区

- 误区：模型会理解公司权限规则。
  - 修正：权限规则必须由代码执行，模型最多辅助解释。
- 误区：JSON Schema 足够安全。
  - 修正：schema 只管格式，业务权限和语义仍要校验。
- 误区：只要用户要求，就可以执行。
  - 修正：用户可能误操作，也可能被诱导；高风险动作仍需确认和审计。
- 误区：工具返回给模型的信息越多越好。
  - 修正：只返回完成任务所需的信息，避免把敏感字段放进模型上下文。
- 误区：开发环境没关系。
  - 修正：开发环境也可能有密钥、客户样本、内部代码和真实外部连接。

## 实践判断

- 什么时候应该采用严格权限：工具访问私有数据、生产系统、外部消息、付款、权限变更、文件写入。
- 什么时候应该谨慎：模型能自由构造 URL、SQL、文件路径、shell 命令或收件人。
- 落地时最先验证什么：越权访问能否被拦截，高风险工具是否确认，工具失败是否可恢复。
- 可观察指标或检查点：权限拒绝率、确认通过率、高风险调用次数、敏感字段过滤次数、工具错误率、人工接管率。
