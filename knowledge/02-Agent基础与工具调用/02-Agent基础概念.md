# Agent 基础概念

## 一句话结论

Agent 是一个由大模型、指令、工具、上下文、状态、权限和评估闭环组成的任务执行系统；它的重点不是“会聊天”，而是能在边界内观察、决策、调用工具并推进任务。

## 概念定位

- 它是什么：面向任务的 AI 系统单元，通常由模型负责理解与决策，由应用负责工具执行、权限控制、状态管理和审计。
- 它不是什么：不是一个神秘的“自动智能体魔法”，也不是把一个聊天模型接上几个函数就天然可靠。
- 相邻概念：chatbot、workflow、tool calling、RAG、memory、planning、guardrails、evaluation。
- 前置知识：大语言模型、prompt 工程、API 调用、JSON、权限控制、错误处理、日志。

初学者可以先记一句话：

```text
普通聊天：模型回答你。
Agent：模型在规则和工具边界内，帮你一步步完成任务。
```

注意：Agent 本身不是缩写。这里的 agent 来自英文“代理人、行动者”的意思，在 AI 语境里指“能代表用户或系统推进任务的执行单元”。

## 核心概念

一个实用 agent 通常至少包含这些部分：

| 组成 | 作用 | 初学者例子 |
| --- | --- | --- |
| Model | 理解用户目标，决定下一步 | 用 GPT 或 Claude 判断用户想查订单 |
| Instructions | 告诉 agent 身份、任务、边界和输出要求 | “你是客服助手，只能查询当前用户订单” |
| Context | 当前任务可用的信息 | 用户问题、历史对话、订单号、权限信息 |
| Tools | 可调用的外部能力 | 查数据库、搜索网页、读取文件、运行代码 |
| Tool router | 决定工具是否可用、如何分发执行 | 根据工具名找到后端函数 |
| Memory | 保存跨轮或跨任务状态 | 记住用户偏好、项目背景、已完成步骤 |
| Guardrails | 护栏和安全边界 | 禁止越权查别人订单，危险动作要确认 |
| State | 当前执行状态 | idle、running、waiting_for_tool、failed、done |
| Trace | 执行轨迹 | 记录模型输入、工具调用、输出、错误 |
| Eval | 质量评估 | 检查 agent 是否选对工具、答案是否有证据 |

核心不是组件越多越好，而是每个组件有明确责任。一个小 agent 可以只有模型、指令和一个安全工具；一个复杂 agent 可能有多个工具、长期记忆、人工确认、轨迹评分和回滚机制。

## 机制与原理

Agent 的基本执行循环可以这样理解：

```text
1. 用户提出目标
2. agent 读取指令、上下文和可用工具
3. 模型判断下一步：直接回答，还是调用工具
4. 如果需要工具，模型生成 tool call
5. 应用侧验证参数、权限和风险
6. 工具执行后返回结果
7. 模型基于结果继续推理
8. 达到停止条件后输出答案或行动结果
9. 系统记录 trace，并用 eval 复盘质量
```

这里最容易误解的是第 4 到第 6 步。模型通常不应该直接执行真实动作，它只是生成“我想调用哪个工具、参数是什么”的结构化意图。真正查数据库、发消息、删文件、扣款、部署代码，必须由应用侧代码执行，并且要经过权限、确认、审计和错误处理。

### Agent 和普通聊天机器人的区别

| 维度 | 普通聊天机器人 | Agent |
| --- | --- | --- |
| 主要目标 | 回答问题 | 完成任务 |
| 外部能力 | 通常没有或很少 | 可调用工具、读取资源、执行动作 |
| 状态 | 多数只靠对话上下文 | 通常需要任务状态、工具状态、权限状态 |
| 风险 | 主要是回答错 | 可能错误执行真实动作 |
| 质量判断 | 答案是否好 | 结果是否完成、过程是否安全、成本是否可控 |

### Agent 和 workflow 的区别

Workflow 是预先写好的流程，像：

```text
收到表单 -> 校验字段 -> 写数据库 -> 发通知
```

Agent 更像：

```text
收到目标 -> 判断需要哪些步骤 -> 选择工具 -> 根据结果调整下一步
```

Anthropic 的工程文章里强调：workflow 的路径主要由代码固定，agent 的路径更多由模型动态决定。这个区分很有用。不要把所有自动化都叫 agent。如果流程非常固定，用 workflow 反而更稳、更便宜、更容易测试。

## 适用场景

- 用户目标开放，无法提前穷举所有流程，例如“帮我分析这个仓库为什么测试失败”。
- 需要多轮决策和工具调用，例如搜索资料、读取文件、写代码、运行测试、再修复。
- 任务结果依赖外部环境，例如数据库、网页、文件系统、业务 API。
- 需要根据中间结果调整策略，例如工具失败后换方法，资料不足时继续检索。
- 希望把 AI 行为做成可观察、可取消、可重试、可审计的产品能力。

## 不适用场景

- 流程固定、规则明确，例如每天 9 点同步报表，用普通定时任务更好。
- 高风险动作没有权限、确认、审计或回滚，例如直接让 agent 自动转账、删库、发公告。
- 任务没有清晰验收标准，例如“帮我变得更成功”。
- 工具和数据质量很差，模型只能在错误信息上继续推理。
- 延迟和成本极端敏感，不能接受多次模型调用和工具往返。

## 前提、边界与反例

- 必要前提：有明确任务目标、可描述的边界、可靠工具、权限模型、失败处理和评估办法。
- 适用边界：agent 能提高开放任务的自动化程度，但不能保证每一步都正确。
- 反例或例外：一个“用户输入城市，后端查天气，模板返回结果”的功能不一定需要 agent，普通 API 流程就够。
- 结论可能失效的条件：模型能力不足、工具描述混乱、权限过宽、上下文被污染、缺少 eval、缺少人工兜底。

## 对比与替代方案

| 方案 | 适合 | 优点 | 风险 |
| --- | --- | --- | --- |
| Prompt-only | 只需要解释、写作、分类 | 快、简单、成本低 | 无法获取新数据或执行动作 |
| RAG | 需要基于资料回答 | 有来源，适合知识问答 | 主要解决“知道什么”，不解决“做什么” |
| Workflow | 固定业务流程 | 稳定、可测试、低风险 | 不灵活，难处理开放任务 |
| Agent | 开放任务、多工具、多轮调整 | 灵活，能推进复杂任务 | 难测试，风险和成本更高 |
| Multi-agent | 多角色协作或评审 | 可分工、可互审 | 复杂度高，容易互相放大错误 |

## 示例或最小实验

最小客服查询 agent：

```text
用户：我的订单发货了吗？

agent 可用工具：
- get_current_user()
- get_order_status(order_id)

执行过程：
1. 模型判断需要订单状态。
2. 如果用户没给订单号，先追问。
3. 如果用户给了订单号，应用侧确认这个订单属于当前用户。
4. 工具查询订单状态。
5. 模型把结果翻译成用户能懂的话。
```

这个例子里，agent 的智能不在于“编一个像真的答案”，而在于：

- 知道什么时候该追问。
- 知道什么时候该调用工具。
- 不越权查询别人的订单。
- 工具失败时能说清楚失败原因。
- 最终回答基于工具结果，而不是凭空猜。

## 失败模式与风险

- 目标误解：用户要“总结文件”，agent 却开始改文件。
- 工具误选：需要读文档，却调用了写入工具。
- 参数幻觉：订单号、文件路径、日期范围看起来格式正确，但实际错误。
- 循环失控：模型不断调用工具，无法停止。
- 权限过宽：一个低风险查询任务拿到了删除或发布权限。
- 上下文污染：网页、文档或工具返回内容诱导 agent 忽略系统规则。
- 结果不可验证：agent 输出“已完成”，但没有证据、日志或可检查产物。
- 成本失控：多轮推理、多工具调用和长上下文导致费用过高。
- 用户失控感：界面不显示 agent 正在做什么，用户不知道能否取消。

## 常见误区

- 误区：agent 越自主越高级。
  - 修正：越自主越需要边界、评估、审计和人工确认。生产系统里“可控”通常比“看起来聪明”更重要。
- 误区：接了工具就是 agent。
  - 修正：工具只是能力。能否围绕目标、状态、权限和失败恢复推进任务，才是关键。
- 误区：agent 可以替代后端业务逻辑。
  - 修正：agent 可以选择和组织行动，但业务规则、权限和数据一致性必须留在确定性代码里。
- 误区：只要模型够强，就不需要 eval。
  - 修正：模型越强，越可能在复杂任务里做出看似合理但难发现的错误，更需要 eval 和 trace。

## 实践判断

- 什么时候应该采用：任务开放、工具选择不固定、中间结果会影响下一步、用户能接受可见执行过程。
- 什么时候应该谨慎：高风险动作、合规敏感数据、权限模型不成熟、缺少评估集、无法解释失败。
- 落地时最先验证什么：工具选择准确率、权限拦截、停止条件、失败恢复、最终结果可检查性。
- 可观察指标或检查点：任务成功率、工具调用成功率、权限拒绝率、循环次数、平均成本、用户取消率、人工接管率。
