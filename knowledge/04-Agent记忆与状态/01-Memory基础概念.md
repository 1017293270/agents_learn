# Memory 基础概念

## 一句话结论

Agent memory 不是“把所有历史都存起来”，而是有选择地保存、更新、读取和删除对未来任务有价值的信息；好的记忆系统必须同时考虑任务价值、权限、隐私、过时、污染和评估。

## 概念定位

- 它是什么：agent 在一次或多次任务之间保留可复用信息的机制，包括用户偏好、项目背景、长期目标、已完成步骤、约束和重要事实。
- 它不是什么：不是完整聊天记录的同义词，不是 RAG，不是数据库本身，也不是让模型“自动变聪明”的魔法。
- 相邻概念：context、session、state、RAG、profile、knowledge base、trace、preference、personalization。
- 前置知识：Agent 基础、tool calling、RAG、权限、数据保留、eval。

初学者可以先记住：

```text
Context 是这次模型调用能看到什么。
Session 是一段连续交互。
State 是当前任务跑到哪一步。
Memory 是未来还能复用什么。
RAG 是从外部资料库检索证据。
```

## 核心概念

### 1. Context

Context 指当前模型调用可见的输入范围，例如系统指令、用户问题、历史对话片段、工具结果和检索资料。

它通常是短期的，会受上下文窗口限制。Context 里出现过的信息，不等于已经进入 memory。

### 2. Session

Session 指一段连续交互或一次任务会话。它可以包含多轮对话、多个工具调用和中间状态。

例如：用户让 agent 修一个 bug，从读取报错、搜索代码、修改文件、运行测试到总结结果，这可以算一个 session。

### 3. State

State 指任务当前状态，回答“现在跑到哪一步”。常见状态包括：

| 状态 | 含义 |
| --- | --- |
| `idle` | 没有任务运行 |
| `running` | 正在执行 |
| `waiting_for_tool` | 等工具返回 |
| `waiting_for_user` | 等用户确认或补充信息 |
| `failed` | 任务失败 |
| `cancelled` | 用户取消 |
| `done` | 任务完成 |

State 主要服务当前任务控制流，不一定应该长期保存。

### 4. Memory

Memory 指经过选择后保存、未来可以再次使用的信息。常见类型：

| 类型 | 例子 | 风险 |
| --- | --- | --- |
| 用户偏好 | 用户喜欢中文、偏好简洁解释 | 误记会导致体验变差 |
| 项目背景 | 项目使用 Next.js、部署在 Vercel | 过时后会误导后续建议 |
| 长期目标 | 用户正在系统学习 agent 工程 | 可能被过度泛化 |
| 约束规则 | 不要直接改 main 分支，先开 PR | 如果上下文变化，需要允许修改 |
| 事实记录 | 某次实验结果、某个决策原因 | 来源不明会污染知识库 |

### 5. RAG 与 Memory 的区别

RAG 主要解决“从大量外部资料里找证据”。Memory 主要解决“跨任务保存对用户或任务有长期价值的信息”。

| 维度 | Memory | RAG |
| --- | --- | --- |
| 主要问题 | 未来要记住什么 | 当前问题要查什么资料 |
| 信息来源 | 用户偏好、历史任务、显式保存的信息 | 文档、知识库、网页、文件、数据库 |
| 生命周期 | 可能跨会话长期存在 | 通常按问题临时检索 |
| 风险 | 隐私、过时、污染、错误个性化 | 召回失败、引用错误、权限泄露 |
| 典型评估 | 该记的是否记住，不该记的是否不记 | 正确资料是否召回并支持答案 |

## 机制与原理

一个较稳妥的 memory 流程不是“看到什么都存”，而是：

```text
1. 识别候选信息：这条信息未来是否有复用价值？
2. 判断类型：偏好、项目背景、长期目标、事实、约束还是临时状态？
3. 检查权限：用户是否允许保存？是否涉及敏感信息？
4. 写入记忆：保存内容、来源、时间、置信度和适用范围。
5. 读取记忆：只在相关任务中取出必要记忆。
6. 更新记忆：新信息与旧信息冲突时，保留变更记录或降低置信度。
7. 删除记忆：用户撤回、信息过时、任务结束或不再需要时移除。
8. 评估记忆：检查是否帮助任务，是否带来错误或泄露。
```

关键点是：memory 应该是有治理的系统能力，而不是模型自由决定的隐藏副作用。

## 适用场景

- 用户长期学习某个主题，需要保留学习路线、已学内容和后续计划。
- 代码 agent 需要记住项目技术栈、测试命令、目录结构和约定。
- 产品设计助手需要记住用户偏好的语气、格式、设计原则。
- 企业助手需要在权限范围内记住项目上下文和工作流状态。
- 多步任务需要在工具失败、用户中断或恢复时接上之前状态。

## 不适用场景

- 临时一次性问题，不需要未来复用。
- 涉及敏感信息但没有明确授权、保留周期和删除机制。
- 事实频繁变化，更适合每次查数据库或 RAG。
- 信息来源不清楚，容易把猜测写成长期记忆。
- 高风险领域中，记忆可能让系统复用过时或错误结论。

## 前提、边界与反例

- 必要前提：有明确的写入规则、读取规则、权限边界、过期机制和用户可撤回路径。
- 适用边界：memory 能改善连续性和个性化，但不能替代事实验证和权限控制。
- 反例或例外：用户说“我今天临时想用英文回答”，这不一定应该成为长期偏好。
- 结论可能失效的条件：用户身份变化、项目切换、旧记忆过时、记忆来源不可靠、权限模型错误。

## 对比与替代方案

| 方案 | 适合 | 优点 | 局限 |
| --- | --- | --- | --- |
| 只用当前 context | 单次短任务 | 简单、隐私风险低 | 无法跨会话延续 |
| Session state | 一次连续任务 | 适合恢复、取消、重试 | 任务结束后通常不保留 |
| Long-term memory | 长期偏好和项目背景 | 个性化、连续性强 | 需要权限、更新和删除机制 |
| RAG | 大量文档和知识库 | 可追溯、可更新 | 不适合保存个人偏好和临时状态 |
| 数据库字段 | 结构化事实和业务状态 | 精确、可审计 | 不擅长开放语义解释 |
| Trace | 调试和审计 | 能复盘过程 | 不应直接等同于 memory |

## 示例或最小实验

任务：让学习助手记住用户正在学习 agent 工程。

候选输入：

```text
我最近在系统学习 agent，重点想搞懂 tool calling、RAG、memory 和 eval。
```

不建议直接保存为：

```text
用户永远只关心 agent。
```

更好的 memory 记录：

```json
{
  "type": "learning_goal",
  "content": "用户正在系统学习 agent 工程，当前重点包括 tool calling、RAG、memory 和 eval。",
  "scope": "learning-assistant",
  "source": "user-explicit",
  "created": "2026-06-23",
  "confidence": "medium",
  "expires_or_review_after": "2026-09-23"
}
```

这个记录保留了适用范围、来源、时间和复查点，避免把短期兴趣误写成永久事实。

## 失败模式与风险

- 过度记忆：把临时偏好、一次性上下文写成长期记忆。
- 记忆污染：模型把自己的猜测或错误总结写入记忆。
- 过时记忆：项目技术栈、业务规则、用户偏好变化后未更新。
- 错误迁移：把 A 项目的约束用于 B 项目。
- 隐私泄露：保存了不该保存的个人信息、密钥、内部资料。
- 权限错配：一个用户或组织的记忆被另一个用户读取。
- 记忆不可见：用户不知道系统记住了什么，无法修改或删除。
- 记忆过强：模型过度依赖旧记忆，忽略当前用户的新指令。
- 无评估闭环：不知道 memory 是否真的提高任务成功率。

## 常见误区

- 误区：历史聊天记录就是 memory。
  - 修正：历史记录只是原始材料，memory 应该是筛选后的、可治理的信息。
- 误区：记得越多越聪明。
  - 修正：低质量记忆会增加噪声、泄露和错误迁移风险。
- 误区：Memory 可以替代 RAG。
  - 修正：memory 保存长期有用信息，RAG 检索外部证据，两者职责不同。
- 误区：模型自己知道该记什么。
  - 修正：写入长期记忆应由产品规则、权限和用户授权控制。
- 误区：删除聊天记录就等于删除记忆。
  - 修正：如果 memory 单独存储，需要独立删除和审计机制。

## 实践判断

- 什么时候应该保存 memory：用户明确表达长期偏好、项目背景、稳定约束或长期目标。
- 什么时候不应该保存：临时指令、敏感信息、来源不明推断、一次性任务细节。
- 落地时最先验证什么：该记的信息是否被正确保存，不该记的信息是否被拒绝保存，读取时是否只取相关记忆。
- 可观察指标或检查点：memory write precision、memory recall relevance、stale memory rate、user correction rate、privacy violation count、task success lift。

## 待验证问题

- 本知识库是否需要单独建立 `memory/` 数据样例，用来测试哪些信息应该被保存。
- 用户偏好、项目背景、学习目标是否应该使用不同 schema。
- Memory 是否应该进入 RAG 索引，还是保持独立存储和独立权限。
- 如何设计一个最小 memory eval：既测“记住该记的”，也测“不记不该记的”。
- UI 是否应该提供“查看、编辑、删除记忆”的入口。
