# Prompt 工程入门

## 我学到的核心点

Prompt 工程不是“写神奇咒语”，而是把你想让模型完成的任务，用清楚、结构化、可测试的方式表达出来。

一个好的 prompt 通常回答 6 个问题：

1. 你要模型做什么任务。
2. 模型需要知道什么背景。
3. 输出应该长什么样。
4. 有哪些限制和不要做的事。
5. 有没有例子能说明好答案是什么。
6. 怎么判断这次回答是成功的。

初学者最重要的转变是：不要只问“怎么写一句万能提示词”，而要问“我有没有把任务、上下文、边界、格式和评价标准讲清楚”。

## 概念定位

- 它是什么：设计、组织、测试和改进输入，让大模型更稳定地产生符合目标的输出。
- 它不是什么：不是关键词堆砌，不是固定咒语，不是能让模型永远正确的魔法。
- 相邻概念：instruction design、system prompt、developer message、few-shot learning、RAG、structured output、eval。
- 前置知识：大模型会基于上下文生成文本；模型输出有不确定性；同一 prompt 在不同模型上可能表现不同。

## Prompt 的基本组成

把 prompt 想成一张任务单。任务单越清楚，模型越少猜。

| 组成 | 作用 | 初学者写法 |
| --- | --- | --- |
| 任务 | 告诉模型要做什么 | “请把下面文章总结成 5 条要点” |
| 背景 | 给模型必要信息 | “读者是刚入门的高中生” |
| 资料 | 给模型可依据的内容 | “只根据 `<article>` 里的内容回答” |
| 约束 | 告诉模型边界 | “不要编造原文没有的信息” |
| 输出格式 | 控制答案形状 | “用 Markdown 表格输出” |
| 示例 | 展示好答案模式 | “输入 A 时，输出应类似 B” |
| 成功标准 | 说明怎么判断好坏 | “答案应能让没有背景的人读懂” |

### 一个最小模板

```text
你要完成的任务：
...

背景：
...

输入资料：
...

输出要求：
- ...
- ...

不要做：
- ...

如果信息不足：
请说明缺什么，不要编造。
```

这不是万能模板，只是帮助初学者避免遗漏关键信息。

## 原理和机制

模型不会真正“读懂你的心”。它只能根据你给出的文本、对话上下文、工具结果和模型自身训练形成的能力，预测应该生成什么。

所以 prompt 的作用可以理解为减少不必要的猜测：

- 任务越明确，模型越知道应该朝哪个方向生成。
- 背景越相关，模型越能选对解释深度和语气。
- 格式越明确，输出越容易被人或程序使用。
- 示例越贴近真实输入，模型越容易模仿正确模式。
- 边界越清楚，模型越不容易越界发挥。

但 prompt 不能保证模型一定正确。它只能提高模型按你意图工作的概率。重要场景还需要测试、检索、工具、结构化输出、人工审核或权限控制。

## 从零开始写 Prompt 的 5 步

### 第 1 步：先写清楚任务

差的写法：

```text
帮我看看这个。
```

问题：模型不知道要总结、翻译、评价、改写，还是找错误。

好的写法：

```text
请阅读下面这段文字，帮我提炼 5 个适合初学者记忆的要点。
```

为什么更好：任务动作明确，输出数量明确，目标读者明确。

### 第 2 步：补充必要背景

差的写法：

```text
解释 RAG。
```

好的写法：

```text
请面向刚学大模型、还不懂向量数据库的人解释 RAG。
要求先用生活类比，再给技术定义，最后说明它解决什么问题。
```

为什么更好：同一个概念给不同读者讲法不同。背景能决定解释深度。

### 第 3 步：规定输出格式

差的写法：

```text
整理一下。
```

好的写法：

```text
请用 Markdown 表格输出，列为：概念、通俗解释、技术解释、常见误区。
```

为什么更好：格式明确后，结果更容易阅读、复制和对比。

### 第 4 步：加入边界和禁止项

差的写法：

```text
回答这个问题。
```

好的写法：

```text
只根据我提供的资料回答。如果资料没有提到，请写“资料中没有足够信息”，不要自行补充。
```

为什么更好：模型容易用已有知识补空白。边界能提醒它不要把外部猜测混进答案。

### 第 5 步：用样例测试和迭代

不要只看一次回答好不好。至少准备 3 类测试输入：

- 普通输入：模型应该顺利完成。
- 边界输入：信息不完整、格式混乱、要求冲突。
- 反例输入：用户要求模型做不该做的事。

如果模型输出不稳定，不要只骂模型。回头检查 prompt 里是否缺了任务、背景、边界、格式或成功标准。

## 常见技巧

### Zero-shot

不给示例，只直接说明任务。

适合：
- 任务简单。
- 输出格式不复杂。
- 模型已经熟悉这个任务。

例子：

```text
请把下面这段话改写得更简洁，保留原意。
```

### Few-shot

给少量输入输出示例，让模型模仿模式。

适合：
- 你想要很具体的风格。
- 输出格式有细节。
- 分类标准不容易一句话说清。

例子：

```text
请按下面示例改写句子：

输入：这个功能非常强大，但是学习成本比较高。
输出：功能强，但上手成本高。

输入：这个页面看起来很漂亮，不过按钮太多让人迷路。
输出：页面漂亮，但操作入口过多。

现在改写：
输入：这个框架生态很完整，不过初学者容易被配置劝退。
输出：
```

注意：示例必须正确且多样。错误示例会把模型带偏。

### 分隔符

用 Markdown 标题、三引号、XML 标签等，把任务、资料、示例分开。

例子：

```text
# 任务
请总结资料中的关键观点。

# 资料
<article>
这里放原文。
</article>

# 要求
- 只根据资料回答
- 输出 5 条
- 每条不超过 30 字
```

为什么有用：模型更容易区分“这是指令”和“这是要处理的资料”。

### 结构化输出

当你希望程序继续处理模型输出时，不要只说“整理一下”，要明确结构。

例子：

```text
请输出 JSON，字段为：
- title: 字符串
- summary: 字符串
- risks: 字符串数组

不要输出 JSON 之外的解释文字。
```

如果是生产系统，最好使用 API 的结构化输出、schema 或工具调用，而不是只靠自然语言要求。

## 不同模型要不同提示方式

不要把一个 prompt 当成所有模型的永久答案。

OpenAI 官方资料里有一个重要提醒：不同模型类型可能需要不同提示方式。尤其是 reasoning models，通常更适合简单直接的提示；强行要求模型“think step by step”不一定有帮助，甚至可能有负面影响。

初学者可以先记住：

- 普通生成任务：清楚写任务、背景、格式和边界。
- 推理任务：写清目标、约束、成功标准；不要迷信“逐步思考”这类固定咒语。
- 工具调用任务：写清工具何时用、何时不用、参数限制和失败处理。
- RAG 任务：写清“只根据资料回答”和“资料不足时怎么说”。

## 什么时候有用

Prompt 工程适合这些情况：

- 你希望模型输出更稳定。
- 你需要固定格式，比如表格、JSON、报告结构。
- 你要让模型适应特定读者、语气或场景。
- 你要把外部资料交给模型总结、提取、对比。
- 你在做 agent，需要规定工具使用、行为边界和失败处理。

## 什么时候容易踩坑

### 误区 1：寻找万能 prompt

没有唯一完美 prompt。prompt 要服务于任务、模型、数据和使用场景。

### 误区 2：越长越好

长 prompt 可能更清楚，也可能更混乱。关键不是长度，而是结构、必要信息和无冲突规则。

### 误区 3：只靠 prompt 解决安全问题

Prompt 能约束输出，但不能替代权限、输入校验、审计和人工确认。比如用户要求删除数据、发消息、支付、改权限，这类高风险动作必须由系统控制。

### 误区 4：格式要求写了就一定遵守

模型可能偶尔偏离格式。生产系统应使用结构化输出、schema 校验、重试或后处理。

### 误区 5：把资料和指令混在一起

如果外部资料里有“忽略上面规则”这类内容，模型可能被干扰。这就是 prompt injection 风险。要用分隔符、权限边界和工具侧校验。

## 初学者练习

### 练习 1：把模糊需求改成清晰 prompt

原需求：

```text
帮我总结这个文档。
```

改写：

```text
请阅读下面文档，面向刚入门的产品经理总结。
输出：
1. 一句话结论
2. 5 个关键要点
3. 3 个可能风险
4. 还需要确认的问题

要求：
- 只根据文档内容回答
- 不要编造文档没有的信息
- 每个要点不超过 40 字
```

### 练习 2：设计一个学习笔记 prompt

```text
我最近学了一个概念：{概念名}

请帮我整理成学习笔记，包含：
- 它是什么
- 它不是什么
- 为什么重要
- 一个生活类比
- 一个技术例子
- 常见误区
- 还需要继续学习的问题

请用初学者能懂的语言写。
```

### 练习 3：给 prompt 加测试样例

如果你的任务是“判断用户反馈是 bug、需求还是咨询”，至少准备：

- 普通反馈：按钮点了没反应。
- 模糊反馈：这个页面怪怪的。
- 混合反馈：按钮点不了，顺便希望能导出 PDF。
- 无关反馈：今天天气不错。

用这些样例测试 prompt，看看模型是否分类稳定。

## 实践判断

- 什么时候应该先优化 prompt：任务明确，但模型输出不稳定、不符合格式、语气不对或遗漏信息。
- 什么时候不该只优化 prompt：模型缺资料、需要实时数据、需要执行动作、需要严格安全控制或需要程序解析稳定结构。
- 落地时最先验证什么：输出是否符合格式，是否遵守边界，是否能处理边界输入，是否会编造资料没有的信息。
- 可观察指标：格式错误率、幻觉率、人工修改率、用户满意度、边界输入通过率、任务完成率。

## 还没搞清楚的问题

- 中文 prompt 和英文 prompt 在同一任务上的稳定性差异有多大。
- 对不同模型，哪些 prompt 结构最容易迁移，哪些需要重写。
- 学习类笔记是否应该固定为同一模板，还是根据主题自动变化。
- 在 agent 场景里，工具使用规则应该放在 prompt、工具 schema、服务端策略还是三者结合。
