# 模型推理与部署

## 我学到的核心点

模型推理是“用已经训练好的模型生成结果”，部署是“把这个推理能力稳定地提供给用户或系统调用”。初学者容易把部署想成“把模型跑起来”，但真正的部署还包括延迟、并发、显存、成本、错误处理、日志、监控、安全和版本管理。

## 推理是什么

训练阶段会更新模型权重；推理阶段通常不更新权重，只使用现有权重处理输入并生成输出。

文本生成常见流程：

```text
输入 prompt
  -> tokenizer 切成 token
  -> 模型计算下一个 token 的概率
  -> 采样或选择一个 token
  -> 把新 token 加回上下文
  -> 重复，直到结束条件
```

这就是为什么输出越长通常越慢：模型不是一次性吐出整段答案，而是一步一步生成。

## 推理中的关键参数

| 参数 | 作用 | 初学者理解 |
| --- | --- | --- |
| max tokens | 限制最多生成多少 token | 防止回答无限变长，也控制成本 |
| temperature | 控制随机性 | 越低越稳定，越高越发散 |
| top_p | 从累计概率范围里采样 | 另一种控制随机性的方式 |
| stop sequence | 遇到指定文本就停止 | 用于控制格式和边界 |
| context window | 输入和输出总 token 范围 | 决定能放多少历史和资料 |
| batch size | 一次处理多少请求或样本 | 影响吞吐和显存 |
| streaming | 边生成边返回 | 改善用户等待体验 |

不要机械套参数。比如写代码、抽取 JSON、事实问答通常需要更稳定；创意写作可以适当提高随机性。

## 部署方式

### 方式 1：直接用模型 API

适合：
- 快速做产品原型。
- 不想维护 GPU。
- 对模型能力和稳定性要求高。

优点：
- 接入快，维护少。
- 通常有较好的模型、工具、监控和安全能力。

缺点：
- 受供应商价格、限流、数据政策影响。
- 对底层推理优化控制少。

### 方式 2：本地或私有化部署开源模型

适合：
- 数据不能出内网。
- 需要控制成本或延迟。
- 需要深度定制模型服务。

优点：
- 数据和部署环境更可控。
- 可以按业务优化模型、量化、缓存和路由。

缺点：
- 需要显卡、推理框架、运维、监控和模型评估能力。
- 表面上模型免费，实际工程成本不低。

### 方式 3：混合部署

常见做法：
- 简单任务用小模型或本地模型。
- 高难任务路由到强模型 API。
- 私密数据先在本地脱敏或检索，再交给外部模型。

这是很多真实系统会采用的路线，因为它兼顾成本、能力和合规。

## 部署时真正要关心什么

| 维度 | 要问的问题 |
| --- | --- |
| 质量 | 回答是否正确、稳定、符合格式 |
| 延迟 | 用户多久看到第一个 token，多久完成 |
| 吞吐 | 同时多少请求能处理 |
| 成本 | 输入、输出、缓存、GPU、运维怎么计费 |
| 可用性 | 模型服务挂了怎么办 |
| 可观测性 | 能否追踪 prompt、模型、延迟、错误和成本 |
| 安全 | 是否泄露数据，是否执行高风险动作 |
| 版本 | 模型升级后行为是否变化 |

## 常见优化方向

### 1. Streaming

流式输出能让用户更快看到进度，尤其适合长回答。它不一定减少总计算时间，但能显著改善体感。

### 2. 缓存

常见缓存：
- Prompt cache：重复长上下文时降低成本或延迟。
- 检索缓存：相同查询不重复查库。
- 结果缓存：固定问题直接复用结果。

风险：缓存可能过期，也可能把不该复用的用户数据复用到错误场景。

### 3. 模型路由

用小模型处理简单任务，用大模型处理复杂任务。

例子：

```text
分类、改写、简单抽取 -> 小模型
复杂推理、代码审查、长文综合 -> 强模型
敏感任务 -> 强模型 + 人工确认
```

### 4. 量化

量化通过降低权重数值精度减少显存和计算成本。它可能带来速度收益，也可能损失质量。不能只看跑得快，还要做任务 eval。

### 5. 批处理

批处理可以提高吞吐，但可能增加单个请求等待时间。适合后台任务，不一定适合实时聊天。

## 部署架构最小图

```text
前端 UI
  -> API 服务
  -> Prompt/上下文构造
  -> 模型路由
  -> 模型 API 或本地推理服务
  -> 输出解析与安全检查
  -> 日志、追踪、成本统计
```

真实系统不要让前端直接裸连模型密钥。模型调用应经过后端服务，以便做权限、审计、限流和错误处理。

## 常见失败模式

- 响应慢：上下文太长、输出太长、模型太大、并发太高。
- 成本爆炸：没有限制 max tokens，没有缓存，没有模型路由。
- 输出不稳定：参数过于随机，prompt 不稳定，模型版本变化。
- 服务不可用：供应商限流、本地 GPU 内存不足、推理服务崩溃。
- 隐私泄露：日志记录了敏感 prompt 或用户数据。
- 调试困难：没有记录模型版本、请求 ID、延迟、token 用量和错误类型。

## 初学者实践路线

1. 先用 API 调通一个最小问答。
2. 加入 streaming，让输出逐步显示。
3. 记录请求、模型、token 用量、耗时和错误。
4. 加入 max tokens 和超时。
5. 做 10 个固定测试样例，观察质量。
6. 再考虑缓存、模型路由和本地部署。
